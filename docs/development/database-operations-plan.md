# Database workload and retention plan

Status: proposed operating plan for DB-09 and DB-10. This document does not enable a monitor, change an index, approve a retention period, or authorize a provider operation. Implemented migrations, deployed migrations, and observed behavior remain separate entries in the cleanup register.

Use [data boundaries](../architecture/data.md), [environment boundaries](environments.md), and the [Supabase deployment workflow](supabase-deployment.md) before applying this plan. Keep each environment's measurements separate. Do not reset statement statistics, vacuum a shared database, or run a destructive query to produce evidence for a review.

### Anonymous-retention repair required before release

Source review found a second defect behind the failing database cron. `delete_old_anonymous_signups()` still deletes `project_signups` directly. That cascades to `waiver_signatures` and loses their Storage paths without inserting deletion-outbox rows. The application archive function records those paths, but previously also deleted certificates explicitly. Releasing only the paper-reference FK repair would let the old cron advance through this unsafe deletion path.

Forward migration `20261007052100_atomic_anonymous_retention.sql` sends both entry points through the same archive transaction and preserves certificates through their existing `SET NULL` reference behavior. It accepts at most 500 IDs and rechecks current linkage, all associated projects, and the thirty-day eligibility boundary. Completed projects require a valid canonical schedule end; cancelled projects require a recorded cancellation time. Only an identity with no project association uses its creation time. An invalid schedule does not become an old orphan. This is a conservative replacement for the old cron's date-only parser.

The write phase locks the anonymous row, its signups, associated projects, and signatures before rechecking eligibility and collecting paths. It uses `NOWAIT` with a per-candidate rollback to avoid waiting on a live signup's project-first lock. A shared cleanup mutex prevents competing workers from processing the same batch. Busy candidates remain for retry; a non-lock failure rolls back the entire batch. Signature assets and immutable source PDFs use the existing bucket-aware reference checks before queueing, so another signature, project, or definition can retain a shared source. Storage draining still happens after database commit, through the existing outbox worker. This migration neither calls Storage nor enables a worker.

The new 38-assertion pgTAP suite covers eligibility shapes and exact finish time, linked identities, direct and secondary project associations, concurrent cleanup refusal, certificate preservation, multi-signer assets, shared source PDFs, late outbox failure, retry, role denial, and the 500-row limit. It remains unexecuted while the owned database is unavailable. The earlier FK tests, existing waiver-outbox tests, new retention suite, and integrated replay are required together before claiming the retention fix is ready.

## Advisor review record

Record one row per stable finding signature, such as schema/table/constraint or schema/function/signature. Each row needs an environment, capture time, statistics reset time, finding type, owner role, and one of these outcomes:

- **Intentional contract.** Link the ACL catalog, constraint, or private-data rule and its executable test. Set a review trigger, such as a new browser caller or changed FK action.
- **Measured work.** Link the costly statement fingerprint, call rate, affected operation, row-count range, current plan, proposed change, and before/after evidence.
- **Violation.** Record the concrete unauthorized path or failure, its impact, and regression coverage. Keep it open until the relevant environment is verified.
- **Insufficient evidence.** State the missing observation. Do not turn this state into an index deletion or policy grant.

An unused-index review must include primary/unique/exclusion constraints, replica identity, dependent queries, infrequent parent deletion, and the age of the statistics window. An unindexed-FK review must consider leading index columns, actual parent mutation frequency, tenant predicates, and the largest affected child table. A low scan count alone never authorizes removing an index.

For an index candidate, compare the actual operation at small and chapter-scale row counts in an owned synthetic database. Include the expensive read and its affected insert/update/delete paths. Save aggregate duration, rows, buffers, index bytes, and plan shape. Use enough repeated runs to expose warm-cache variation, and report the sample count. A favorable single run is not an acceptance result. Production `EXPLAIN ANALYZE` on a write remains a write, even inside a transaction intended for rollback.

## Proposed health measurements

The platform maintainer owns collection and the database maintainer owns interpretation. The CSF maintainer owns plugin operation labels and retention dependencies. These are responsibilities to assign, not claims that a person is already on call.

Keep the health payload to counts, durations, sizes, operation names, and opaque statement fingerprints. Exclude SQL bind values, student records, recipient addresses, object paths, source sheets, and provider error bodies. Retain capture time and reset time with every cumulative metric; an unknown or stale sample is a distinct state from zero.

| Signal                  | Proposed review threshold                                                                                | First response                                                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Database job progress   | A failed run, or no fresh result after three expected intervals                                          | Confirm cron identity, last successful domain progress, and bounded error category. A cron success does not prove the domain advanced. |
| Project schedule health | Any invalid published schedule, or a last run older than 15 minutes                                      | Use the bounded Admin Overview list. Confirm intended event dates with the organizer before correction.                                |
| Durable queue health    | An expired claim still holding unresolved work, or oldest eligible work exceeding three worker intervals | Compare eligibility, lease state, retries, and unknown provider outcomes. Never blindly retry an unknown send or creation.             |
| Lock health             | Any new deadlock or a sustained increase in lock-wait duration                                           | Identify the operation pair and lock order. Reproduce synthetically before changing transaction boundaries.                            |
| Temporary writes        | A sustained rate above the prior comparable interval, with the same reset boundary                       | Attribute spills to statement fingerprints before changing work memory or query shape.                                                 |
| Relation growth         | More than 20 percent in a week for a relation above 50 MB, or double its reviewed baseline               | Distinguish retained evidence, queue backlog, indexes, and dead tuples. Size growth starts a review; it does not trigger deletion.     |

These starting thresholds require review against a complete school-term workload. Do not present them as capacity estimates or deployed alerts. The collection task must record the actual hosting plan, disk headroom, connection headroom, and workload window before setting environment-specific limits.

## Acceptance before enabling a retention change

Name the owning workflow and exact eligible states. Produce a sanitized preview count, age range, retained-reference count, and blocker count under the intended tenant scope. Store a sealed preview or equivalent request receipt when the domain already requires one. Commit must revalidate the same subject set and permissions while holding the domain's concurrency locks.

The synthetic test must cover another tenant, a still-referenced row, an unresolved provider attempt, retrying the same request, a crash after database commit but before Storage acknowledgment, and a late concurrent writer. Verify that the retained audit and tombstone records can explain the operation without restoring removed identity fields. Use forward migrations and reviewed lifecycle functions rather than an untracked SQL sweep.

Before a destructive hosted change, record the available backup/PITR coverage and a restore rehearsal on disposable infrastructure. A configured backup does not prove restore success, and a database backup does not automatically recover external Storage or provider objects. Current backup coverage and restore timing remain unverified by this local plan.
