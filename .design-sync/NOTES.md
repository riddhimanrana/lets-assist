# design-sync notes — lets-assist

## Repo shape

This repo is the whole Next.js app, not a standalone component-library package.
`components.json` (shadcn config) shows the reusable UI lives in `components/ui/`
(shadcn primitives) and `components/shared/` (a handful of app-wide shared
components). Everything else under `components/` (`admin/`, `auth/`,
`organization/`, `projects/`, CSF-plugin UI, etc.) is domain/business-logic UI,
deliberately out of scope for this sync — confirmed with the user at sync
start. No Storybook exists in this repo (checked `.storybook/` and
`*.stories.*` — none found), so this always runs the **package shape** in
**synth-entry mode** (no `dist/`, no shipped `.d.ts`).

## PKG_DIR trick

`cfg.entry` points at `.design-sync/.manual-entry.mjs` (regenerated by
`gen-entry.mjs`, gitignored) instead of leaving `entry` unset. This is
deliberate: without an `--entry` override, `PKG_DIR` is derived as
`<node-modules>/<cfg.pkg>`, which doesn't exist for an app-embedded DS. Passing
`--entry` makes `package-build.mjs` walk up from the entry file to the nearest
`package.json` with a `name` field — since the entry lives under
`.design-sync/` (no package.json there), that walk lands on the **real repo
root** `package.json` (`name: "lets-assist"`), so `PKG_DIR` = repo root. This
makes `cssEntry`/`tsconfig`/`componentSrcMap` paths all resolve naturally
relative to the repo root, and keeps `cfg.pkg` ("lets-assist-ui") free to be a
clean display name / preview import specifier, decoupled from directory
resolution.

`cfg.srcDir` is explicitly set to `"components"` — the default heuristic order
(`src` → `lib` → `components`) would otherwise match the repo's real `lib/`
directory first (it exists), which contains `lib/plugins/private` (the CSF
private submodule — must never be scanned per AGENTS.md's non-negotiable
boundaries). Since every one of the 90 synced components is pinned explicitly
via `componentSrcMap`, `srcDir`'s broader walk (it still covers all of
`components/`, including out-of-scope subdirs like `organization/`) is only
ever used as an enrichment/fallback pool and never actually leaks unwanted
components into the discovered set — but keep `srcDir` scoped to `components`
on any future edit; never let it default to `lib`.

## Component curation

Raw PascalCase exports across `components/ui` + `components/shared` = 329
(most are compositional subparts: `DialogTrigger`, `TableRow`,
`AlertDialogPortal`, etc. that only render meaningfully inside their parent).
Curated down to root-level components (one per logical widget) = 95,
confirmed with the user. Further excluded from that 95, each for a concrete
reason (not just "hard to render"):

- **`BotVerificationDialog`, `TurnstileComponent`** — depend on
  `@/components/auth/SecureCheckPanel`, `@/hooks/useBotVerification`, and
  `@/lib/auth/secure-check` (real anti-bot/security logic tied to site keys).
  Not a reusable visual primitive; app security surface, out of scope by the
  same spirit as AGENTS.md's caution around security-sensitive code.
- **`QueryMessageToast`** — pure `next/navigation` side-effect component (no
  visual surface of its own), not meaningful as a browsable DS entry.
- **`ProfileHoverCard`, `OrganizationHoverCard`** (both in
  `components/shared/ProfileHoverCard.tsx`) — import `next/link`. Bundling
  real `next/link` internals via esbuild pulls in Next's client runtime, which
  references `process.env.__NEXT_MANUAL_CLIENT_BASE_PATH` outside the
  `process.env.NODE_ENV` pattern esbuild's `define` covers — `process` isn't
  polyfilled in the IIFE, so this crashed the **entire** bundle at module init
  (all 92 components missing from `window.LetsAssistUI` — a single bad module
  in the `export *` graph takes down every export). Confirmed via
  `grep -rln "next/link\|next/navigation\|next/router\|next/image"
  components/ui components/shared` — these two were the only offenders beyond
  QueryMessageToast (already excluded). If re-including either: cfg has no
  esbuild-alias knob for this — would need to fork `lib/bundle.mjs`
  (`cfg.libOverrides`) to alias `next/link` to a stub, which touches the
  app-contract surface the skill says not to fork.

Final count: **90 components** (`.design-sync/config.json` `componentSrcMap`
is the authoritative, committed list — the generator script scratch file is
gitignored).

## Default-export handling

`gen-entry.mjs` emits `export * from '<file>'` per unique source file, PLUS an
explicit `export { default as <Name> } from '<file>'` for any component whose
source uses `export default` (`export *` never forwards a default export).
Only `LocationAutocomplete` needed this (`export default function
LocationAutocomplete(...)` in `location-autocomplete.tsx`) — caught via
`[BUNDLE_EXPORT] 1/90 not a component on window.LetsAssistUI`.

## Styling: compiled Tailwind v4, not copied globals.css

This app uses Tailwind v4's CSS-first config (`app/globals.css` starts with
`@import "tailwindcss";`). The converter's `cssEntry` just copies the file
verbatim — it does NOT run a Tailwind build. Copying `globals.css` as-is would
ship an unresolved `@import "tailwindcss"` and zero generated utility classes
(every component would render unstyled). Fixed with
`.design-sync/compile-tailwind.mjs`, which runs the real `postcss` +
`@tailwindcss/postcss` (both already repo deps) against `app/globals.css` from
the repo root (Tailwind v4 auto-scans the whole project for class usage) and
writes real compiled CSS to `.design-sync/.compiled/tailwind.compiled.css`
(gitignored build output) — that's `cfg.cssEntry`. This step is folded into
`cfg.buildCmd` (`compile-tailwind.mjs && gen-entry.mjs`) — **always re-run
`cfg.buildCmd` before `package-build.mjs`**, plain `next build`/`next dev`
will NOT regenerate this file.

## Fonts

`next/font` (the `geist` npm package for Geist Sans/Mono, plus three
`next/font/local` fonts: OverusedGrotesk, Nohemi, cheese-milky — see
`app/layout.tsx`) injects `@font-face` at build time; none of it appears in
`globals.css`, so the scrape finds nothing on its own. Hand-authored
`.design-sync/fonts.css` (committed, real durable input — NOT the compiled
output) with real `@font-face` rules pointing at the actual shipped files
(`node_modules/geist/dist/fonts/...`, `public/fonts/...`, `app/fonts/...|`),
wired via `cfg.extraFonts`.

**Gotcha**: `extractFonts` (`lib/css.mjs`) only extracts `@font-face { ... }`
blocks out of an `extraFonts` CSS file — any other rule (e.g. a `:root { --font-geist-sans: ...; }`
variable binding) is silently dropped. The `--font-*` CSS variable bindings
that Tailwind's `font-family` utilities actually reference must ship from
somewhere `extractFonts` doesn't touch — they're appended directly onto the
compiled Tailwind output in `compile-tailwind.mjs` instead (see the
`fontVarBindings` block there). If a font var still shows in `[TOKENS_MISSING]`
after adding a font, check it's bound in `compile-tailwind.mjs`, not just
`fonts.css`.

**`[FONT_MISSING] "Cambria"`** — accepted as a substitute, not sourced.
Cambria is a licensed Microsoft system font referenced only as a generic serif
fallback (Tailwind's default `font-serif` stack) — not one of this app's real
brand fonts, and not legally redistributable. The DS pane renders it with a
system serif fallback; this is expected and fine.

## Known non-blocking gaps (pre-existing in the source app, not introduced here)

- **`[TOKENS_MISSING]` sidebar tokens**: `--sidebar-background`,
  `--sidebar-foreground`, `--sidebar-primary(-foreground)`,
  `--sidebar-accent(-foreground)`, `--sidebar-border`, `--sidebar-ring` are
  referenced by `app/globals.css`'s `@theme` block (`--color-sidebar: var(--sidebar-background)`
  etc.) but **never actually defined** anywhere in `app/globals.css`. This is
  a real gap in the app itself, not something introduced by the sync — worth
  flagging to whoever owns the sidebar component, but not this sync's job to
  invent values for. `--accordion-panel-height` is set at runtime by
  base-ui's own JS (inline style) — expected to be absent from static CSS.

## Re-sync risks

- `.design-sync/.compiled/`, `.manual-entry.mjs`, and the node_modules stub
  are all gitignored/regenerated — a re-sync on a fresh clone MUST run
  `cfg.buildCmd` before `package-build.mjs`, or the build will use a stale or
  missing compiled stylesheet / entry file.
- If new components are added to `components/ui` or `components/shared` later,
  they will NOT auto-appear — `componentSrcMap` is a fully explicit allowlist
  by design (to keep the private submodule and business-logic dirs out of
  scope). Add new entries by hand.
- If a future shadcn/ui update changes `next/link`/`next/navigation` usage in
  any currently-included component, watch for the same whole-bundle
  `process is not defined` crash this sync hit with `ProfileHoverCard.tsx`.
